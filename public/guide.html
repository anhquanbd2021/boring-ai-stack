Stage-by-stage guide

Six stages, four owners, one rule

Every stage in the pipeline is owned by exactly one layer. A tool earns its place by owning its stage — remove the tool and the stall lands exactly where its job was.

Teaching model, honest limits. This simulates the discipline, not the tools — no real agents run here. The point is the topology: where work stalls when a job has no owner.

Start here

What this demo proves

With all four layers enabled, three work items travel the full pipeline and land in done with a spec, context pack, change set, approval, and release record each. Remove the orchestrator and every item stalls at context — unrouted. Remove the governor in untracked mode and items still reach done, but recover() fails because no release record exists. That is "durable and recoverable" made testable.

The four layers

One job per tool

Layer 01

Workspace

Owns idea: turns a raw idea into a structured spec — title, scope, acceptance. The first artifact the pipeline carries.

Missing it
Raw ideas pile up at intake; nothing becomes buildable.
Layer 02

Orchestrator

Owns context and learn: assembles the context pack, routes work onward, and writes the retrospective that feeds the next idea.

Missing it
Structured work stalls unrouted — you become the message bus.
Layer 03

Builder

Owns build: takes spec + context pack, returns a change set with its trade-offs recorded. The session is disposable; the artifacts are not.

Missing it
Specs and context accumulate; nothing executes.
Layer 04

Governor

Owns review and ship: the review gate, the version, the release record. The audit trail that makes AI-assisted work recoverable.

Missing it
Work ships untracked — or never ships. Either way, no way back.

The handoff contract

State, not vibes

Try to skip a stage and the handoff is rejected — the next stage can only do its job if the previous one shipped its artifact.

Inspect the evidence

npm run check    # both
npm start        # serve the lab on :3000

Everything is deterministic — the same scenario always stalls at the same stage.

Limits

What this demo does not claim

  • It models the discipline, not the tools — no real agent, tracker, or git host is involved.
  • Stages process instantly; real queues have latency, retries, and partial failure.
  • recover() models rollback via a release ledger; real recovery also needs backups and deploy history.
  • One item flows at a time per stage per tick — contention and priorities are out of scope.
